    PRD Status Check

    Section-by-section against PRD v0: what's actually implemented in the codebase today, what's deliberately deferred per MVP Scope v0, and what's genuinely missing.

    Status: Draft Version: v0 Date: July 15, 2026 Owner: Jackson Zhou Depends on: PRD v0, MVP Scope v0

    1. Method

    This report reads directly against the codebase (android/, backend/) as of this date, not against either the MVP Scope report's own claims or the Implementation Walkthrough's narrative — those are good context but can drift from what's actually in the repo. Every "Implemented" verdict below traces to a specific file. Status is one of:

    • Implemented — built and present in the running app/backend, at least to MVP-heuristic depth (not necessarily the PRD's full version).
    • Partial — a real subset exists, or the data model/backend is ready but the client doesn't use it yet, or vice versa.
    • Not started — no code for it exists anywhere in the repo.
    • Deferred (by design) — MVP Scope v0 explicitly cut this from MVP; its absence is a decision, not a gap.
    Headline The core loop from MVP Scope Section 7 — capture → parse → confirm → track → export — is real and runs end-to-end on Android against a real Firebase project (contempo-platform), with real Google Sign-In. Almost everything missing against the full PRD is exactly what MVP Scope said to cut (PMS integration, geofencing, bank signals, household logging, wearables, SMS). The gaps worth attention are the small number of things MVP Scope itself called in-scope that aren't built yet (Section 3 below) — photo capture and the print/PDF export, specifically.

    9. Data Model & Security (backing PRD §6 broadly)

    Not a PRD section on its own, but worth stating plainly since everything above depends on it: Firestore (contempo-platform, standard edition, us-central1), real Google Sign-In (Credential Manager + Google Identity Services, with an emulator-only fake-identity path for local dev), and firestore.rules/storage.rules both enforcing request.auth.uid == uid. A security-rules audit run alongside this report found no cross-user access risk, but flagged the rules have no field-level type or size validation on any document — worth tightening before real users are writing to it, independent of PRD feature coverage.

    10. Go-to-Market & Success Metrics (PRD §9, §10)

    Entirely non-technical sections — trust moat, distribution, pricing, retention framing, success metrics. Nothing here is "implementable" in the codebase sense; they're unaffected by this status check. Worth flagging only that MVP Scope §10's exit criteria ("still logging weekly by week 8," correction rate, etc.) require the app to actually be in a pilot host's hands generating real usage data — the loop is now real enough to run that clock (Implementation Walkthrough §10), but no usage data exists yet to evaluate against those criteria.
