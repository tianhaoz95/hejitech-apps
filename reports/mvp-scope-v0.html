    MVP Scope

    The narrowest build that tests the actual unknown — whether frictionless capture changes logging behavior — without chasing feature parity with better-funded competitors before that's proven.

    Status: Draft Version: v0 Date: July 14, 2026 Owner: Jackson Zhou Depends on: PRD v0

    1. Purpose of This Document

    PRD v0 describes the full product — passive signal fusion, a legal-grounding copilot, household constraint checking, wearable capture, a concierge audit-defense tier. Almost none of that should ship on day one. This document cuts that scope down to an MVP: the smallest build that tests the product's actual hypothesis and gets real hosts logging real hours, without spending months on infrastructure the hypothesis might not even need.

    2. The MVP Hypothesis

    What we're actually testing Hosts fail material participation not because the strategy doesn't work, but because logging doesn't survive a busy year. The bet is that removing capture friction — no form, no app-open requirement, talk or text it — measurably changes whether a host is still logging in November. Everything else in the PRD is either in service of that bet (trust, so hosts believe the record holds up) or a moat layered on after the bet is confirmed (passive signal fusion, integrations, household features).

    If frictionless capture doesn't change logging behavior, no amount of passive-signal sophistication or legal-copilot depth saves the product. So the MVP should isolate and test that one mechanism as cheaply as possible, not build the full moat first.

    3. Scoping Principle

    Cut toward the untested part of the hypothesis; defer anything whose main job is closing a competitive gap rather than testing the mechanism above. Concretely: PMS/Airbnb/VRBO integration is explicitly out of MVP — it's the deepest engineering investment in the whole feature set, and it's a parity play against STR Loophole, not a test of the friction hypothesis. The same logic cuts geofence, bank/Plaid signals, and smart-lock access — all real differentiators eventually, all deferred until the core loop is validated.

    4. In Scope for MVP

    4.1 Capture

    • Manual entry form — full fields, always available, the baseline
    • Natural-language text entry, parsed into structured fields (property, task, duration, category) with one clarifying question when needed
    • Voice memo capture, transcribed and parsed the same way as text
    • Photo attachment as evidence on any entry

    4.2 Trust & review

    • Every AI-drafted entry lands pending, requiring one-tap confirm or edit before it's final
    • Every field on every entry editable after the fact, regardless of capture method
    • Basic contemporaneity flag: entries logged more than N days after their activity date are marked, visibly, on the entry itself
    • Basic vague-entry flag: very short or generic descriptions prompt for one more detail before they're accepted

    4.3 Output

    • Simple pacing dashboard: hours logged vs. the selected test's threshold, with a projected finish date at current pace
    • CSV export
    • A minimal print/PDF view of the entry list — not the full narrative CPA package from the PRD, just something a host can hand over today

    4.4 Platform

    • Android app (Section 6) — text, voice, manual, and photo capture all live here at MVP; the SMS gateway is deferred (Section 5.1)
    • A minimal web app: export and account settings only, not a capture surface

    6. Platform Sequencing

    Decided Android first, iOS fast-follow. The demographic assumption in the earlier draft of this section (STR hosts skew iOS) is exactly the kind of thing this section said should override the default — and it just did. The first actual pilot user is Android, which settles the question more reliably than a demographic guess: build for the person who's really going to use it before the person who might.

    This also means the Android/Wear OS feasibility research from earlier in this project (Quick Settings tile as the hands-free trigger, Wear OS Tiles/Widgets, Android 16's Live Updates via Notification.ProgressStyle) stops being a parity check and becomes the actual MVP platform spec — worth re-reading with that lens before build starts.

    • Android ships first, native (Kotlin/Compose, not cross-platform) — chosen specifically because it integrates more directly with Wear OS and native platform libraries than a cross-platform framework would, which matters given Wear OS capture is an explicit fast-follow target (Section 5.1), not a someday-maybe.
    • iOS fast-follow, sequenced right after the core loop is validated with the pilot user rather than run in parallel from day one — same reasoning as before, just the other direction: shared backend keeps the second platform cheap once the first proves the loop works.
    • The SMS gateway is no longer a day-one channel — it's deferred (Section 5.1). At MVP, the Android app itself (text/voice/manual/photo) is the only capture surface.

    7. Core MVP User Flow

    StepWhat happens
    1. CaptureText, speak, or manually fill the form. No passive signals yet — every entry starts from a deliberate action.
    2. ParseThe agent extracts property, task, duration, and category, asking one clarifying question only if it can't infer confidently.
    3. ConfirmThe draft sits pending until a one-tap confirm or edit. Nothing is final without this step, on any entry.
    4. Track & exportThe pacing dashboard shows progress toward the chosen threshold; CSV or print export hands the record to a CPA on request.

    8. Architecture Notes for MVP

    Decided Backend: Firebase — Firestore for entry storage (its built-in offline persistence directly serves the PRD's "works without signal, syncs when back in range" requirement), Firebase Auth, Storage for photo evidence, and FCM for push nudges. The agent/LLM layer is built on Genkit (Firebase's open-source server-side AI framework), which covers the MVP tool-calling (log_entry, flag_risk), the confirm/edit step as a human-in-the-loop pattern, and gives a natural home for the legal-copilot RAG when that moves beyond curated FAQ. Chosen over standing up bespoke infrastructure before the core loop is validated — consistent with the scoping principle in Section 3.
    Decided Model: latest Gemini Flash via Firebase AI Logic, with on-device Gemini Nano used through Firebase AI Logic's hybrid-inference API during MVP to save cost — PREFER_ON_DEVICE mode, falling back to cloud automatically. This is an experimental Google feature as of mid-2026, so build against its real constraints rather than assume parity with cloud: on-device inference only runs while the app is in the foreground, only supports English and Korean (cloud fallback is the only option for any other locale), and caps at 4,000 tokens for the entire on-device request. None of these block the MVP loop — capture is a foreground, English-language interaction by default — but they do mean on-device can't quietly cover background/passive parsing later without falling back to cloud anyway.
    Decided Local dev: Firebase Emulator Suite, not a live Firebase project — the pilot user is creating the real project in parallel, so the app, Genkit functions, and Firestore rules are all built and tested against firebase emulators:start first, and pointed at the real project only once it exists. This also means Firestore security rules should be written and tested from day one rather than deferred, since the emulator suite tests them for free as part of local dev.
    • Agent tools at MVP: only log_entry and flag_risk (basic heuristic version) from the PRD's full tool set. split_time, query_case_law (as live RAG), and check_household_constraint wait for fast-follow.
    • Build the correction-feedback pipeline now, even unused. Log every edit a user makes to an AI draft as structured data from day one, even before any personalization logic consumes it — this is cheap to capture now and impossible to backfill later. The PRD's data-flywheel advantage (Section 8) depends on not losing this window. Firestore's native BigQuery export is a convenient fit for this — capture it as an append-only collection now, worry about querying it for personalization later.
    • Legal copilot ships as curated FAQ, not live RAG. A well-written static knowledge base (grounded in IRS Pub 925 and §1.469-5T, per the PRD) phrased through an LLM is materially cheaper than a dynamic case-law retrieval system, and tests whether hosts actually use this feature before that infrastructure is built.
    • Contemporaneity and vague-entry flags are simple heuristics at MVP (days-since-activity threshold; description length/specificity check), not the fuller scoring model implied by the PRD's readiness dashboard.
    • Build gotcha to design around, not discover mid-build: a single Gemini API call can't both offer tools and force responseMimeType: application/json — they conflict on the same request. Doesn't block the loop, since function-call arguments are already structured/schema-conforming data on their own (that's what log_entry's arguments are); reserve responseSchema for turns where no tool is being offered, don't reach for it on tool-calling turns.

    10. Exit Criteria — What Graduates MVP to Full Build-Out

    Narrowed from the PRD's full success-metrics list (Section 10) to what's actually measurable in an 8–12 week beta:

    • Beta hosts are still logging weekly by week 8 — the actual hypothesis test
    • Median time from activity to log entry stays low (contemporaneity is working, not just theoretically available)
    • Correction rate on AI-parsed entries is low enough to indicate the parsing is genuinely saving effort, not just relocating it to constant editing
    • At least a handful of beta hosts reach or are clearly on pace for their chosen hour threshold

    If these hold, the passive-capture and integration investment in Sections 5.2 and the PRD's full vision are justified. If they don't, that's a cheaper failure to learn from than after building PMS integrations first.

    11. Risks Specific to This Scope

    Competitive exposure Cutting PMS integration means MVP launches without a capability STR Loophole already has. This is an accepted trade — the MVP isn't trying to win on integration depth, it's trying to prove the friction hypothesis cheaply — but it means the MVP is not yet competitively differentiated on that axis, only on capture friction and trust framing. Worth revisiting the timeline for Section 5.2 if STR Loophole ships a legal copilot or contemporaneity scoring before this product reaches Phase 3.
    Single-platform gap iOS is excluded for the beta window by design (Section 6) — acceptable because the primary goal of that window is validating the loop with the actual first pilot user, not maximizing reach. Worth a deliberate checkpoint before Phase 2 (Section 9) on whether wider beta recruiting needs iOS sooner than "right after the core loop is validated."

    12. Open Decisions Before Build Starts

    Platform, backend, model, and local-dev setup are now all decided (Sections 6 and 8). What's left:

    • Whether the curated legal FAQ content is written in-house or reviewed by the CPA/tax-attorney advisor named in the PRD's trust-moat strategy (Section 9.1) before launch
    • Exact timing for standing up the SMS/Twilio gateway (Section 5.1) — deferred out of MVP for logistics reasons, not technical ones, so this is a "when the pilot user has bandwidth" question rather than an architecture question
