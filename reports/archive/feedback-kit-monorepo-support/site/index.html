Natively supporting monorepos in FeedbackKit

The HEJI repo (tianhaoz95/hejitech-apps) holds two apps, Waypack and Wee Hours, each with its own FeedbackKit project. FeedbackKit already copes with several projects pointing at one repo. What it lacks is the idea of where in the repo a project lives. This walkthrough proposes one new setting, a project root directory, and follows it through every part of the loop.

Already works

  • One repo, many projects. The GitHub webhook matches every project whose github_repo equals the pushed repo (.ilike("github_repo", …) in supabase/functions/github-webhook).
  • Unambiguous linking. FeedbackKit: <id> trailers carry the report id, so a fix can't be credited to the wrong app.
  • Per-project releases. Release tokens belong to one project, so a Wee Hours build only ships Wee Hours fixes.

Gaps

  1. Prompts don't say which app or folder. An agent infers it from the project id buried in a screenshot URL.
  2. The CLI can't tell where you are. In a monorepo it stops with "You're in several projects" unless you pass --project.
  3. Issues from every app land in one repo, unmarked. Agent-runner workflows fire on a shared label and run at the repo root.
  4. Release matching ignores paths. A mistyped trailer on another app's commit goes unnoticed.
Proposal in one line: add projects.github_path (for example projects/weehours; empty = repo root) and use it in the prompt, the CLI, GitHub issues and the release check. Projects map to apps; products stay platforms within an app (iPhone, Watch, web).

3The prompt

The prompt is what an agent (or you, pasting it) acts on. Today it says nothing about the app or where its code is. Three new placeholders fill that in: {{project_name}}, {{repo}} and {{project_path}}. The default template opens with them.


          

        

        
The template is rendered in four places, and each needs the placeholders: the Edge Function (supabase/functions/_shared/promptTemplate.ts), the dashboard (web/src/lib/prompt-template.ts), the CLI (cli/src/promptTemplate.ts) and the Mac developer app (DeveloperApp/Sources/Services/PromptGenerator.swift), plus the merged multi-report prompt (renderMergedPrompt), which should group reports by project.

5CLI: which project?

        
A committed feedbackkit.json in each app's folder says which project it is. The CLI walks up from the current directory to the nearest one, the way git finds .git. Click a folder to see what each command would use.

        

          

          

        

        
// projects/weehours/feedbackkit.json (written by `feedbackkit init`)
{ "projectId": "71d85688-ffc5-481c-8636-2b94dc5c1c90", "path": "projects/weehours" }

        
Precedence: --project > FEEDBACKKIT_PROJECT_ID > nearest feedbackkit.json > your only project. With --token, the token decides, and the CLI warns if it disagrees with the folder.

      


      
      

        
6Release check

        
feedbackkit release ships every linked fix whose commit is an ancestor of the build. With a root directory, it can also check that each fix commit touches that directory, which catches a trailer pasted onto the wrong app's commit. Toggle the commits in the build, then announce it.

7Data model

        
One column, plus a stable label slug. Everything else derives from them.

        
        
-- supabase/migrations/0030_project_path.sql
alter table projects
  add column if not exists github_path text not null default ''
    check (github_path !~ '(^/|/$|\.\.)'),            -- relative, no leading/trailing slash, no ..
  add column if not exists github_label text not null default '';  -- '' = derived slug, e.g. fk:weehours

-- Several projects may share a repo, but not the same folder of it.
create unique index if not exists projects_repo_path_uniq
  on projects (lower(github_repo), github_path) where github_repo is not null;

9Graduation and compatibility

        

          

            
When an app leaves the monorepo

            
HEJI apps can graduate to their own repo and backend. In FeedbackKit that's an edit of two fields: github_repo to the new repo, github_path to empty. Report history, releases and tokens stay with the project; nothing references the old folder.

            

          

          

            
Compatibility

            
    
              
  • Existing projects get github_path = '': same prompts (the new header just names the app and repo), same CLI behavior, same issues.
    • 
              
  • Custom templates keep working; the placeholders are opt-in, and only the default template uses them.
    • 
              
  • feedbackkit.json is optional; the old precedence still applies when there's none.
    • 
              
  • The path check warns rather than blocks at first; make it an error once projects have set their paths.
