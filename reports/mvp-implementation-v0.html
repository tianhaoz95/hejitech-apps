    MVP Implementation Walkthrough

    What got built against the MVP scope report, how the pieces fit together, what's still unverified, and exactly how to run it.

    Status: Draft, unreviewed Version: v0 Date: July 15, 2026 Owner: Jackson Zhou Depends on: MVP Scope v0

    1. What's Here

    A working scaffold of the MVP core loop from the scope report's Section 7 (capture → parse → confirm → track → export), built as a native Android app (Kotlin + Jetpack Compose) against a Firebase/Genkit backend, structured as a monorepo that also has room reserved for iOS, Wear OS, and web without needing to be restructured later.

    Update: compiled and run end-to-end, not just written This was first written blind (no Android SDK available), then actually built and tested once an SDK was found on this machine — real compile errors were found and fixed (Section 6.1), and the full loop was run on a real emulator: captured an entry, confirmed it, watched it write to a live Firestore emulator, and saw it appear on the Dashboard. Section 6 has the honest before/after; Section 7's run instructions are now based on what actually worked, not what was expected to.

    2. Repository Layout

    PathWhat it is
    android/app/The phone app — MVP screens, live here
    android/core/Shared data models + Firestore repository, used by app now and wear once Wear capture starts
    android/wear/Minimal placeholder Wear OS module — compiles and installs, shows "coming soon." Real Wear capture is fast-follow (MVP scope Section 5.1)
    backend/Firebase project root — Firestore/Storage rules, emulator config, and the Genkit Cloud Functions
    backend/functions/Genkit flows: parseEntry (cloud fallback for parsing) and flagRisk (contemporaneity/vagueness heuristics)

    branding/, reports/, scripts/Unchanged — the landing page mockup and planning docs from before this build

    3. The Core Loop, As Built

    Matches MVP scope report Section 7 exactly, one screen per step:

    StepScreen / fileWhat happens
    Captureui/capture/CaptureScreen.ktType, or tap the mic for Android's built-in speech-to-text (RecognizerIntent) — transcription lands in the same text field, nothing STT-specific downstream
    Parseagent/AgentClient.ktHybrid on-device/cloud — see Section 4
    Confirmui/confirm/ConfirmScreen.ktSame screen serves both "review the AI draft" and "manual entry from scratch" — see the callout below
    Trackui/dashboard/DashboardScreen.ktConfirmed hours vs. a hardcoded 100-hour STR threshold, plus the entry list with risk flags shown inline
    Exportui/export/ExportScreen.ktCSV generated on-device, shared via Android's share sheet
    Design choice worth knowing about Confirm and manual entry aren't two screens — ConfirmScreen is the full editable field set either way. Tapping "Enter manually instead" on the Capture screen just navigates straight there with empty fields. This is the PRD's "manual and AI-drafted entries carry the same weight" principle showing up as one less screen to build and keep in sync, not just a policy statement.

    4. Hybrid On-Device / Cloud Parsing

    AgentClient.parseEntry() tries on-device Gemini Nano first (Firebase AI Logic hybrid inference, PREFER_ON_DEVICE), and falls back to the cloud parseEntry Genkit flow whenever the on-device attempt throws, isn't available, or its response doesn't parse as valid JSON.

    Neither path uses tool-calling. That's deliberate, not a missing feature: Firebase's own docs confirm function calling isn't available for on-device inference at all, and a single Gemini call can't offer tools and force schema-shaped JSON output on the same request (the MVP scope report's Section 8 gotcha). Instead, EntryDraftSchema is a single self-describing shape — needsClarification plus either a complete draft or a clarifying question — so one structured-output call handles both the happy path and the "I need one more detail" path. Cloud gets a real enforced schema (Genkit's output: { schema }); on-device gets a carefully worded prompt asking for the same shape as plain text, best-effort parsed.

    Real constraints on the on-device path, not hypothetical Per Firebase's hybrid-inference docs: foreground-only (won't run if the app is backgrounded), English and Korean only, and a roughly 4,000-token cap on the whole request. None of these block the MVP loop — capture is a foreground, English-language interaction by default — but they're the reason on-device can't quietly absorb background/passive parsing later without falling back to cloud anyway.

    Update (Section 9): the original version of this class always requested PREFER_ON_DEVICE and silently fell back to cloud on any failure — which meant there was no way to actually confirm on-device inference was doing anything rather than quietly billing cloud on every call. Settings now exposes a user-controlled InferencePreference (On-device only / Prefer on-device / Cloud only) that AgentClient reads on every call; "On-device only" deliberately does not fall back — see Section 9.3 for the real device test that proves this.

    5. Data Model & Security

    Firestore, nested under a single owner (no household/team sharing yet — fast-follow per the MVP scope report):

    PathContents
    users/{uid}/properties/{id}Property names
    users/{uid}/entries/{id}Log entries — status, source, category, risk flags, timestamps
    users/{uid}/corrections/{id}The correction-feedback pipeline: AI value vs. final confirmed value, per field, written whenever they differ at confirm time

    firestore.rules and storage.rules both just check request.auth.uid == uid — this was smoke-tested by actually starting the emulator suite against these exact rules files (Section 6.3), not just checked for valid syntax.

    Update (Section 9): anonymous auth has been replaced with real Google Sign-In. MainActivity's AuthGate now renders a SignInScreen (instead of an indefinite spinner) until auth.currentUser is real, so nothing hits Firestore before a real signed-in uid exists. uid-scoped rules didn't need to change — swapping the auth method just changes which uid ends up in that slot.

    6. What Was Actually Verified, and What Wasn't

    This section originally described a build that had only been reasoned about, not run. An Android SDK turned up on this machine (~/Library/Android/sdk) after this report was first drafted, so everything below is now from an actual build, not just static inspection.

    6.1 Real bugs found by actually compiling, and fixed

    Eight, across three build attempts, before the first clean build:

    • Root build.gradle.kts never declared the com.android.library plugin even though core/build.gradle.kts applied it — caused a "plugin already on the classpath with an unknown version" failure before a single Kotlin file even compiled.
    • core module used FirebaseAuth without depending on it — only firebase-firestore was declared; FirestoreEntryRepository needed firebase-auth too.
    • A same-named class/function collision — MainActivity.kt had a @Composable fun ContempoApp() in the same package as the ContempoApp Application subclass. Kotlin genuinely can't disambiguate a zero-arg composable call from a zero-arg constructor call with the same name — real "overload resolution ambiguity" compile error. Renamed the composable to ContempoRoot.
    • Wrong package paths for Firebase AI Logic's hybrid-inference types — the previous draft of this report flagged GenerativeBackend/InferenceMode/OnDeviceConfig as "inferred, not confirmed." They were wrong. Resolved by decompiling the actual downloaded firebase-ai-17.13.0.aar with javap rather than guessing again: InferenceMode and OnDeviceConfig live directly under com.google.firebase.ai; GenerativeBackend and PublicPreviewAPI are under com.google.firebase.ai.type.
    • HttpsCallableResult.data isn't accessible as a Kotlin property on this SDK version despite a public Java getter — Kotlin's metadata marks it private for property-access purposes. Fixed by calling .getData() explicitly as a method.
    • ExposedDropdownMenu isn't a top-level composable in Compose Material3 1.3.1 (the version this BOM resolved to) — it's a member of ExposedDropdownMenuBoxScope, called with an implicit receiver. The import itself was invalid and had to be removed, not fixed.
    • A missing padding import and a leftover unbalanced brace from an earlier hand-edit, both simple mechanical mistakes.
    • No network security config for cleartext traffic to the Firebase emulators. This one didn't show up as a compile error — the app built and launched fine, but anonymous sign-in against the local Auth emulator silently never completed (stuck on AuthGate's loading spinner indefinitely). Android blocks cleartext HTTP by default for apps targeting API 28+; Firebase's useEmulator() calls use plain HTTP to 10.0.2.2. Fixed with a debug-build-only network security config (app/src/debug/res/xml/network_security_config.xml + a matching debug-only manifest override) so release builds stay locked down.

    6.2 The actual end-to-end test that was run

    Not a simulation — an installed AVD (Pixel 7 profile, API 36.1/"Baklava," Google Play system image, arm64 for Apple Silicon host acceleration) running the real app-debug.apk against a real firebase emulators:start --project demo-contempo instance:

    1. App launched cold — no crash, FirebaseInitProvider initialized successfully, themed UI rendered correctly (confirmed via screenshot, including the pine-green AuthGate spinner in the correct brand color).
    2. Anonymous sign-in completed against the Auth emulator once the network security config fix landed — AuthGate correctly revealed the Capture screen.
    3. Navigated Capture → "Enter manually instead" → Confirm screen — all fields (Property, What you did, Duration, Category dropdown with all 6 EntryCategory values) rendered and accepted input correctly.
    4. Filled in a real entry ("Maple St" / "Cleaned pool and restocked towels" / 35 min / maintenance) and tapped Confirm.
    5. The write reached Firestore and succeeded — the emulator's own debug log briefly showed a real, since-fixed problem (google-services.json's placeholder project ID didn't match the emulator's demo project, so the very first attempt failed with Invalid app id; corrected the local test file's project ID to demo-contempo to match).
    6. App auto-navigated to the Dashboard, which displayed the just-saved entry — property, task, duration, and formatted timestamp all correct — with the hours-toward-threshold bar showing progress.
    One thing this test does NOT cover The on-device/cloud AI parsing path (AgentClient.parseEntry) wasn't exercised — that requires a real Gemini API key and a deployed (or locally-served) parseEntry Genkit function, neither of which exist yet. The test above used the manual-entry path deliberately, since it's the one piece of the loop that doesn't depend on external credentials. Testing the AI path is the natural next verification step once a GOOGLE_GENAI_API_KEY exists.

    6.3 Still not verified

    • The AI parsing path itself (see callout above) — on-device Gemini Nano and the cloud parseEntry Genkit flow have never actually run.
    • The Genkit backend has never been built (tsc) or deployed — only its config/rules were exercised, not the TypeScript itself.
    • The Wear OS placeholder module compiles (confirmed) but has never been installed on a Wear emulator or device.
    • Photo capture, CSV export/share, and voice-to-text (RecognizerIntent) are implemented but untested — none were exercised in this pass.
    • Gradle/AGP/Kotlin/Compose BOM versions in libs.versions.toml are whatever resolved successfully during this test (AGP 8.7.2 explicitly warned it was "tested up to compileSdk 35," not the 36 used here) — it built clean despite the warning, but a newer AGP is worth picking up when convenient rather than treating this pairing as final.

    7. How to Run It

    7.1 Backend + emulator

    1. cd backend/functions && npm install
    2. cd .. && firebase emulators:start --project demo-contempo
      Runs fully offline against a demo project — no real Firebase project needed yet. Emulator UI at http://localhost:4000.
    3. Optional, only if you want to poke at parseEntry directly without the app: export GOOGLE_GENAI_API_KEY and run npx genkit start -- npm --prefix functions run build:watch for the Genkit dev UI.

    7.2 Android app

    The steps below are what actually worked in this build, not the original guess.

    1. JDK 17, not whatever's newest. This machine also had JDK 26 on PATH by default, which is too new for this Gradle/AGP pairing. Point JAVA_HOME at a JDK 17 install before building — Android Studio bundles its own compatible JDK automatically if you use its UI instead of a terminal.
    2. If opening in Android Studio: let it generate the Gradle wrapper on first sync. From a terminal instead, with no gradlew committed yet: download any Gradle 8.x distribution once, then run its bin/gradle wrapper --gradle-version 8.11.1 from inside android/ to generate gradlew — this is a one-time bootstrap.
    3. local.properties needs sdk.dir=/path/to/Android/sdk (see local.properties.example) — Android Studio writes this automatically; from a terminal, write it by hand.
    4. google-services.json's project ID must match whatever Firebase project (real or demo) you're actually pointing at — this surfaced as a real failure in testing: a placeholder project ID compiles fine but every Firestore write silently fails with Invalid app id until it matches. For local emulator testing before the real project exists, set project_id/storage_bucket to demo-contempo (matching the --project demo-contempo flag in Section 7.1) rather than leaving the literal placeholder text in place.
    5. Run on an emulator or a device with Google Play services. Debug builds point at 10.0.2.2 for the Firebase emulators — that's the special alias the Android emulator uses to reach your host machine; replace it with your machine's LAN IP in ContempoApp.kt if you're running on a physical device instead. The debug-only network security config (Section 6.1) already permits cleartext to that host — nothing extra to configure there.
    If you want a GUI step-by-step instead Everything above assumes a terminal for the actual click-through — ask directly for a walkthrough of any specific step (e.g. "walk me through creating the Firebase Android app and downloading google-services.json") and it'll be spelled out with exact menu paths rather than assumed here.

    7.3 What "working" looks like

    This is no longer a prediction — it's what was actually observed, screenshot by screenshot, in Section 6.2.

    1. App launches to a brief spinner (anonymous sign-in), then the Capture screen.
    2. Type or speak an entry, e.g. "cleaned the pool and restocked towels, about 35 minutes" — or tap "Enter manually instead" to go straight to the same field set with nothing pre-filled.
    3. Typed path: it parses (on-device first, cloud fallback), lands on Confirm with fields pre-filled. Manual path: same Confirm screen, empty. Both were confirmed to render correctly, including the category dropdown's full set of options.
    4. Confirm (editing anything first, if you want) — it writes to Firestore and bounces to the Dashboard. Confirmed working against a live Firestore emulator.
    5. Dashboard shows the entry and updated hours-toward-threshold. Confirmed — property, task, duration, and timestamp all displayed correctly for the saved entry.
    6. Export screen generates a CSV and hands it to the Android share sheet. Implemented, not yet exercised in a live test.

    9. Round 2: Google Sign-In, Settings, Verified On-Device Testing, Agent Chat

    After using the round-1 build, four gaps were flagged directly: no real login, no way to control the app's behavior, no way to actually confirm on-device inference was being used rather than silently falling back to cloud, and no way to ask the agent a free-form question. This section covers what changed and — same standard as Section 6 — what was actually run, not just written.

    9.1 What changed

    • Google Sign-In replaces anonymous auth. New auth/AuthManager.kt branches on BuildConfig.USE_FIREBASE_EMULATOR: the real path uses Credential Manager + Google Identity Services (GetGoogleIdOption, needs a GOOGLE_WEB_CLIENT_ID in local.properties once a real Firebase project exists); the emulator path skips Google entirely and hands the Auth emulator a small fixed fake-identity JSON as the "ID token" — see the callout below for why that's not a hack.
    • Settings screen (ui/settings/), reached via a gear icon in a shared top bar rather than a 5th bottom-nav tab. Two sections: Account (signed-in name/email, sign out) and AI model (the inference-preference toggle below).
    • InferencePreference enum (agent/InferencePreference.kt) — On-device only / Prefer on-device / Cloud only — persisted via a plain-SharedPreferences-backed AiSettingsStore, read fresh by AgentClient on every call rather than baked in at construction time.
    • Chat (ui/chat/), a 4th bottom-nav tab ("Ask"). New askAgentFlow Genkit flow (backend/functions/src/flows/askAgent.ts) answers free-form questions grounded in the host's own logged hours, with an explicit "not tax/legal advice" framing baked into the prompt. History is in-memory only for this round (no Firestore persistence) — a deliberate scope cut, not an oversight.
    • ParseSource (on-device vs. cloud) is now threaded through to the Confirm screen as a small caption, so a parse's origin is visible instead of invisible.
    The emulator sign-in trick, explained The Firebase Auth emulator doesn't verify federated (Google/etc.) ID tokens against the real provider — it decodes whatever string is passed as the token and, if it parses as JSON, takes sub/email/name as the resulting user's claims. So AuthManager's emulator path builds that JSON locally and calls signInWithCredential(GoogleAuthProvider.getCredential(json, null)) directly — no Google Identity Services call, no real Firebase project, no SHA-1 fingerprint, no OAuth Web Client ID needed to exercise the whole sign-in → Firestore-scoped-by-uid → sign-out loop right now. The real Credential Manager path is fully implemented alongside it, just not exercisable until a real Firebase project exists.

    9.2 Real bugs found by actually compiling and running this round

    • Nested block comment broke the whole file. A doc comment containing the literal text flows/*.ts — Kotlin, unlike Java, nests block comments, so the /* inside that path fragment silently opened a second comment; the outer comment's closing */ then closed the wrong one, leaving the rest of the file "inside" an unclosed comment. Fixed by rewording the comment, not by any special escaping (there isn't one).
    • InferenceMode.ONLY_ON_DEVICE/PREFER_ON_DEVICE needed @OptIn(PublicPreviewAPI::class) at every call site, not just where the GenerativeModel is constructed — referencing the enum constants themselves is also gated by the experimental-API annotation.
    • Chat's input field hid behind the keyboard. Found live, on-device: ChatScreen's root Column had no imePadding(), so on this edge-to-edge activity the bottom-anchored input row could end up rendered underneath the software keyboard instead of above it. One-line fix (Modifier.imePadding()), but only findable by actually opening the keyboard on a real screen — this is exactly the kind of bug static review or a compile check can't catch.

    9.3 The actual tests that were run

    Same AVD (Pixel 7, API 36.1) and Firebase emulator suite as Section 6.2, with adb reverse forwarding all four emulator ports (see scripts/run-android-with-emulators.sh, written for a physical device but the same port-forwarding applies to an AVD):

    1. Sign-in / sign-out loop: cleared app data to force a clean SignInScreen, tapped "Sign in with Google," and confirmed via logcat (FirebaseAuth: Notifying auth state listeners about user (...)) that the fake-credential path produced a real signed-in user. Settings correctly displayed the fake identity's name/email ("Pilot Host" / "pilot@example.test") — proving the emulator's JSON-decoding behavior works exactly as documented.
    2. "On-device only" fails loud, not silent: selected "On-device only" in Settings, submitted a manual capture. The on-device model isn't actually available on this AVD, and — as designed — the app showed "On-device model unavailable — no cloud fallback" instead of quietly calling cloud. Confirmed via the Functions emulator log that parseEntry was never invoked: this is the direct fix for "I can't tell if on-device is actually being used."
    3. "Cloud only" actually reaches the cloud function: switched to "Cloud only," submitted the same capture — this time the app displayed a real error surfaced from Google's own GenAI client library ("Please set a valid API key…"), proving the parseEntry callable really was invoked over the network this time (it fails only because no GOOGLE_GENAI_API_KEY is configured in this environment — the same pre-existing, already-flagged gap from Section 6.3, not something new).
    4. Chat round-trip: sent a real question ("Will cleaning count toward my 100 hours") from the Ask tab — the user bubble rendered correctly, ChatViewModel called AgentClient.askQuestion, which (Cloud only still selected) called the new askAgent callable and got the same expected missing-API-key error back, rendered as the chat's error state. Full plumbing confirmed working end to end; only the actual LLM answer is blocked on a real API key.
    Still not verified Everything that needs a real GOOGLE_GENAI_API_KEY — actual on-device Gemini Nano inference (this AVD doesn't have the model available at all) and actual LLM answers from either parseEntry or the new askAgent. The backend TypeScript does now build clean (npm run build in backend/functions, verified this round — round 1 had never actually run tsc, only the config/rules files were exercised).
