HQ: the autopilot CEO of a repo

HQ is a new, self-contained product that runs scheduled agents to find maintenance, reliability, performance and opportunity work across a repo, turns what they find into evidence-backed proposal cards, and builds, verifies and ships the approved ones. You spend about 10 minutes a day in a web and iOS inbox approving, rejecting or discussing. Brand-new product ideas stay with you; everything else is managed.

Decided

  • Self-contained and portable. HQ works on any repo that has a .hq/ folder; this monorepo is its first customer.
  • HQ owns control, not capabilities. It decides when things run, where results land and who approves. Skills and scripts keep doing the work.
  • Opinionated, not coupled. Built-in opinions (card schema, tiers, evidence rule); no knowledge of project paths or tools.
  • Agent-agnostic. Claude, Antigravity or another agent can be the CEO; one entry point, hq.get_context.
  • A product, not a self-hosted tool (v2). Any team signs up; one workspace = one repo + its members. HQ is opinionated that the repo is a monorepo (§10).
  • Guardrails live in HQ's code, never in prose an agent might misread.

Not decided

  • Pushed branches/PRs vs local-only branches (changes heji-build-next's policy).
  • Whether HQ may run TestFlight/Beta releases on its own.
  • Weekly budget, name, backend, where HQ's code lives long-term.
Recommendation: review the three contracts (§4 card schema, §5 .hq/ spec, §6 headless skill contract) first. Everything else in HQ is implementation behind them, and they're the expensive part to change later.

Problem and goals

The monorepo already has most of the capabilities an autopilot needs, but every one of them waits for you to start it, and their results land in different places.

Capabilities exist.claude/skills/ holds 17 repo skills, among them heji-fix-ci, heji-update-toolchain, heji-build-next, heji-archive-reports. Release goes through scripts/cut_release.sh; isolation through scripts/check_isolation.mjs and scripts/graduation_check.sh.
Triggering is manualThe skills run when you ask. Only CI has schedules (16 of the 62 workflows in .github/workflows/ have a schedule:, e.g. the weekly TestFlight runs).
State is scattered49 report folders in reports/ and reports/archive/, each its own site and port; open owner steps live in agent memory notes; CI, TestFlight and Even Hub each have their own place to look.
Hand-offs are copy-pasteReview sites end in "Copy summary, paste to any agent". That works, but nothing tracks whether the hand-off happened.

Goals

  1. One queue and one audit log for all non-creative work across the repo.
  2. Owner time ≤ 10 minutes a day (target) to keep the repo healthy and moving.
  3. Every proposal carries evidence; every shipped change carries proof it works.
  4. Nothing dangerous happens without you, whichever agent is the CEO.
  5. Portable: adopting HQ in another repo means adding .hq/ and connecting the MCP.

Non-goals

  • Originating brand-new products. HQ may surface ideas as cards (open question Q2); it never starts one alone.
  • Replacing CI/CD. GitHub Actions, Workers Builds and cut_release.sh stay the delivery path.
  • Absorbing skills. HQ calls skills; it doesn't contain copies of them.
  • Submitting to App Store review, touching secrets, deleting data, or placing trades. Always human.

Architecture

Toggle Today / Proposed. Today you are the scheduler and the queue. With HQ, scouts and the CEO feed a single inbox, and an executor that holds the credentials runs verbs only after HQ's policy check.

Contract 1: the proposal card

Every scout, the CEO and every executor speaks this one format. hq.create_proposal validates it and refuses cards without evidence or with a tier above the project's ceiling.

Card lifecycle: proposed → approved | rejected | discussing → building → in_review → shipped | failed. L0 cards go straight from proposed to building and show in the digest afterwards.

Contract 2: the .hq/ folder

Repo-specific knowledge lives in the repo, laid out like a skill folder: HQ.md (YAML frontmatter that HQ enforces, plus prose guidance agents read) and bin/ verbs HQ calls. It nests like CLAUDE.md: a root .hq/ for repo-wide policy and one per project, which moves with the project when it graduates.

Verbs

Rules

  1. Verbs are adapters, not implementations. bin/release is a one-line wrapper around scripts/cut_release.sh, which stays the only release path. A verb that grows real logic means that logic belongs in the project's own scripts.
  2. No duplication of CLAUDE.md. How to build and test stays there; HQ.md covers goals, priorities, scouts and limits.
  3. Not a third home for skills. HQ.md references skills by name; .hq/ never contains them.
  4. Existing config stays put. release.env and backend.env are read by verbs, not moved.
  5. The whole folder is L3. Any change to .hq/ needs your approval, including HQ's own suggestions.
  6. Learned taste becomes an HQ.md edit. Repeated rejections turn into a proposed change you approve, so what HQ learned is visible, versioned and moves with the repo.

Contract 3: skills that run headless

A skill becomes a scout without being rewritten: in headless mode it does its usual investigation and then emits cards instead of a review site or chat answer. The same skill still works by hand.

Agents, the CEO role and the MCP

One entry point, three ways in. hq.get_context(repo, project?) returns the merged HQ.md policy plus live state (inbox, budget left, open PRs, recent decisions). Every route leads there, so the context never depends on how the agent arrived.

MCP tools (first set)

Agent adapters

One small adapter per agent: how to start it headless, pass the prompt, attach the MCP and collect output. Claude Code via claude -p; Antigravity and others through whatever headless mode they offer.

Not verified: which headless/CLI modes Antigravity and other agents support today. Check before promising an adapter.

CEO comparison: because adapters make the CEO swappable, HQ can run two CEOs on the same week's signals and compare them by approval rate, evidence quality and cost.

Autonomy tiers

Each HQ.md sets a tier_ceiling per project, and each verb its own tier. A project can be promoted a tier after a track record (e.g. 4 weeks with no reverted L1 merges; threshold to be decided). Promotion is itself an L3 HQ.md change.

Workspaces, members and sign-in (v2)

HQ is a product any team can adopt, not a tool each team deploys. Its one opinion about tenancy: a workspace is one repository and the people who work on it, and HQ is built for that repository to be a monorepo (one root .hq/, one .hq/ per project inside). A single-project repo works too (root .hq/ only). Teams with several repositories either consolidate or create one workspace per repository; workspaces share nothing.

ConceptRule
WorkspaceOne repo (owner/name), its synced .hq/ policy, its cards, runs, health, tokens and audit log. Everything HQ stores carries a workspace_id.
MembersPeople with a role in that workspace. Whoever creates it is its first admin; others join through an invite link.
Rolesadmin: members, invites, tokens, kill switch, policy sync · approver: approve, reject, ship, build again, run any verb including L3, start runs · viewer: read and comment (a comment still asks the agent to answer).
Sign-inThrough the shared Supabase project: Google and Apple now, GitHub once its provider is enabled (every workspace is a GitHub repo, so it's the natural default). One person can belong to several workspaces and switches between them.
Runners and agentsTokens belong to a workspace (hq_run_…, hq_agt_…). Each workspace runs its own runners and pays its own agent costs; HQ never holds its code-signing or deploy keys.
IsolationRow-level security: a signed-in person reads only rows of workspaces they belong to. Writes go through the Worker, which checks the role first. A workspace token can't see or touch another workspace.
Repo connectionv2: hq sync with a workspace runner token. Later: a GitHub App installed on the repo (sync, CI status, PRs without a checkout).
Not yet decided: billing and plans, and whether membership should mirror the repo's GitHub collaborators once the GitHub App exists.

Verbs declare runs_on in HQ.md, so HQ routes each job to the cloud or to the Mac runner.

HQ's own data (cards, decisions, audit log) lives in its own hq schema and never reads another project's database. HQ touches projects only through the repo, CI status, verbs and public APIs. This exception, a project whose job is to open PRs everywhere while holding no runtime coupling to any project, should be written into supabase/GRADUATION.md.

Isolation check

  • CI greps HQ's code for projects/, product names and cut_release; any hit fails.
  • A smoke test runs HQ against a blank fixture repo with only a .hq/ folder.
  • hq lint checks every .hq/: frontmatter schema, declared verbs exist and are executable, side-effecting verbs pass --dry-run.

Migration: moving the scattered tools in

What moves into HQ is the triggering, the output and the approval, not the skills themselves. An old entry point retires only after HQ has handled its job for a few weeks without you falling back to it.

Stays where it is: cut_release.sh (HQ triggers it through bin/release), the weekly TestFlight crons and project CI, project-specific checks such as projects/weehours/scripts/asc_build_status.swift (HQ reads what they report), and heji-candidate-review for visual design choices.

Phases and success measures

The build is quick by this repo's track record; calibration isn't. Good proposals, a useful taste file and enough trust for L0 merges take weeks of real runs, which is why cards start flowing in phase 1 and the portal polish runs alongside calibration.
