Multiple children in one household

The database already has room for several children; the apps assume one. The work is to make each child a first-class part of the household on every surface, without slowing down one-tap logging.

1Overview

Already works

  • weehours.babies is its own table (household_id, name, birth date)
  • Every event already carries baby_id (events.baby_id, LogEvent.babyId)
  • Sync (outbox + seq cursor), RLS and realtime are per household, so they need no change
  • Caregivers, duty, invites, billing are household-wide, which stays right with more children

Gaps

  • Household has one babyId/babyName; my_household() joins one baby; update_household renames every baby
  • Derivation runs over the whole household: twins fed together are flagged as duplicates, and one child's open feed blocks the other's
  • captures (glasses voice) has no baby_id; the interpreter knows no names
  • Widgets, Live Activity, Siri, Watch, glasses, MCP, the account page and CSV all show one child

Proposal: derive everything per child (status, sessions, duplicates, reminders), keep the household as the unit for people, duty and billing, give each child a few settings of their own, and pick the target child on every surface the same way: a name said or chosen wins; otherwise the surface's current child. On the phone that's the Log-for bar (03), which I recommend.

3Data model

One migration in supabase/schemas/weehours/schema.sql (via scripts/db_migration.sh weehours multi-child). Events don't change: they already have baby_id.

-- babies: per-child settings, order, archive
 create table weehours.babies (
   id uuid primary key,
   household_id uuid not null references weehours.households(id) on delete cascade,
   name text not null,
   birth_date date,
+  settings jsonb not null default '{}'::jsonb,   -- color, bottle_ml, default_feed, reminders (D2)
+  position int not null default 0,
+  archived_at timestamptz,
   created_at timestamptz not null default now()
 );
+create policy "members add babies" on weehours.babies for insert with check (household_id = weehours.my_household_id());

-- captures: which child the glasses were focused on (null = let the transcript decide)
+alter table weehours.captures add column baby_id uuid;

-- RPCs
+add_baby(p_id, p_name, p_birth_date, p_settings)          -- members only
+update_baby(p_id, p_name, p_birth_date, p_settings, p_archived)
-update_household(p_id, p_name, p_baby_name, p_birth_date, p_settings)   -- renamed every baby
+update_household(p_id, p_name, p_settings)
 my_household()  -- adds "babies": [{id, name, birth_date, settings, position, archived_at}] ordered by position;
                 --   keeps baby_id / baby_name / birth_date = first active child, for older app builds

Swift Household gains babies: [Baby] (with active = not archived); babyId/babyName become computed from the first child so existing call sites keep compiling while they move over. TypeScript (packages/core, services/web/src/account.ts, apps/glasses/src/api.ts) gets the same babies array. spec/event-types.json documents the optional group field (D4).

4Derivation per child

Bug today if a second child existed: Sam logs Mia's bottle on the phone at 1:52 and Alex logs Leo's on the watch at 1:52. Derive.swift step 4 flags “same type, close in time, other caregiver” as a possible duplicate; and openFeedSession() sees one household-wide open feed, so finishing Leo's bottle would close Mia's.

DerivedLog(events, babyId:) derives over one child's events; the app keeps a [UUID: DerivedLog]. Duplicate detection, sessions, next side, growth, the status line and ReminderPlanner all become per child. Duty and household system events (duty) stay household-wide (D3). The same change goes into packages/core/src/core.ts, and spec/fixtures/status.json gets twin fixtures (simultaneous bottles aren't duplicates; finishing one child's feed leaves the other's open) so Swift and TypeScript stay locked together.

5Voice & captures

  • Names are parsed deterministically, like times and quantities (Parsers in Decision.swift): the children's names and nicknames (“Mia”, “Leo”), plus “both / the twins / everyone / the babies”. The Laya questions stay category × phase, so model accuracy doesn't change.
  • No name → the current child (D5). Two names in one sentence (“Mia had 90, Leo 110”) → one event each, with each amount split by the parser.
  • The confirmation bar always names the child: “Bottle · 90 ml · Mia”.
  • Glasses captures store the focused child in captures.baby_id; the phone that processes them uses it when the transcript has no name.

7Compatibility

  • Older app builds keep working: my_household() still returns baby_id/baby_name for the first child, and they log to it. But once a second child exists, an old build would log everything to the first child, so “Add a child” in the new build first asks everyone in the household to update (step 1 adds the app version to each event's provenance, so the app can tell who is still on an old build).
  • Existing data needs no backfill: every event already points at the household's single baby.
  • Local-only households (no account) work the same; Store.rehome moves to a per-child map instead of one baby.
  • Graduation rules are untouched: everything stays in the weehours schema.

8Plan & effort

  1. Data + derivation: migration, Household.babies, per-child DerivedLog in Swift and TS, twin fixtures. No UI change yet; single-child households behave exactly as today.
  2. Phone: Settings → Children, onboarding, the chosen Now design, Timeline chips/filter, per-child reminders, voice name parsing.
  3. Extensions: widgets, Live Activity, Siri, Watch.
  4. Glasses, MCP, website, CSV.
  5. Verify on the iPhone with a twins household (-localSetup gains a second child) and screenshots of each surface; MCP checks in scripts/test-mcp.mjs.

Overall: L (about 4 focused sessions). Step 1 is the riskiest and lands first, behind no flag, because it changes nothing for one child.
