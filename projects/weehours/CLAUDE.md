# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this project. Wee Hours lives in `projects/weehours/` of the HEJI monorepo: read the root `CLAUDE.md` too (releases, the shared Supabase project). Paths below are relative to `projects/weehours/` unless they start at the repo root.

Wee Hours is a newborn log (feeds, diapers, sleep, growth: weight, height, head size) for iPhone, Apple Watch, widgets/Siri, Even Realities G2 glasses + R1 ring, and AI agents over MCP. Every input becomes one typed, append-only event log shared by a household. `docs/decisions.md` records product and architecture decisions the user made explicitly. Read it before proposing architectural changes, and don't reintroduce rejected options: no server-side inference, one unified on-device decision model, Supabase rather than CloudKit (now the Supabase project every HEJI app shares). The full design walkthrough is in `report/v0/site` (`report/v0/script/serve.sh`).

```bash

# Laya fine-tuning pipeline (synthetic data, DGX Spark; see ml/README.md)
cd apps/ios/LogCore && swift run -c release logeval --export "$PWD/../../../ml/runs/laya_export.json"
cd ml && python -m weehours_ml verify --config configs/pilot.toml && python -m pytest -q

# TypeScript (npm workspaces from the repo root: @weehours/core, @weehours/glasses, @weehours/web)

# Backend (from the repo root: one Supabase project for every HEJI app)

scripts/db_migration.sh weehours <what>          # after editing supabase/schemas/weehours/*.sql (repo root)
```

## Architecture

**`spec/` is the single source of truth.** `event-types.json` holds the event types, fields and decision questions. `calibration.json` holds the fitted per-question temperatures, and `fixtures/status.json` holds derivation fixtures. `scripts/sync-spec.sh` copies them into `apps/ios/LogCore/.../Resources`, the LogCore test fixtures and `packages/core/src/`. Edit `spec/` and then sync; never edit the copies.

**Derivation exists twice and is fixture-locked.** `apps/ios/LogCore` (`Derive.swift`, `Status.swift`) and its TypeScript twin `packages/core/src/core.ts` (`@weehours/core`) both turn the event log into sessions, duplicates and the one-line status ("Fed 2h40m ago · left next · …"). The MCP Worker, the account page and the glasses app use the TS copy (`packages/core/test/core.test.ts` runs the fixtures). Both must pass `spec/fixtures/status.json`, so a behaviour change goes into both implementations and the fixtures.

**Voice pipeline (on the phone only).** WhisperKit transcribes, then LogCore's decision layer (`Interpreter.swift`, `Decision.swift`, `LayaPrompt.swift`) asks Laya questions shaped as category × phase rather than one flat type question. Clock times, relative times and quantities (ml, weight, length) are parsed deterministically, not by the model, and so is the choice between weight, height and head size inside the `growth` category (`Parsers.growthMeasure`), which has no phases. Calibrated confidence picks a tier: auto-commit, pick from two, or full list. A sentence the model is as sure isn't a log entry ("none of these" at the auto bar) is kept as a note without asking, with a "Log it" toast to reopen the list (`Interpretation.isNotALog`); the keyword fallback never does this, since no keyword match isn't evidence. Timed activities (spec `timed`: tummy time, play, walks) start and stop from their Now tile: an entry with `ongoing: true` that `stopTimed` edits into one with its minutes, so every household phone shares the timer. `ReminderPlanner` adds one quiet "still going?" nudge (no escalation) when an open bottle, nursing session, daytime nap (spec `sessionReminders`) or timed activity (`remindAfterMinutes`) runs past its norm. The Speak widget (Home and Lock Screen) and the Speak control (Control Center) open `weehours://voice`. Settings → Voice → Quick capture (per phone, off by default; `QuickCapture.key`) logs the top guess instead of asking, with a "Change" toast (`processVoice(quickCapture:)`, `reopenCapture`); glasses captures processed during sync still ask. The `DecisionModel` backends are in `apps/ios/App/Sources/Services.swift`: on-device Laya (`apps/ios/LayaRuntime`, a Swift port of llama.cpp's server-side decision path that runs on `apps/ios/Vendor/llama.xcframework`), a llama-server on the Mac for development, and a keyword fallback. Models are bundled from `apps/ios/App/Models` (`scripts/fetch-models.sh`, git-ignored); `eval/laya.env` names the Laya model in use (repo, file and `LAYA_REVISION`, the Hugging Face tag of the run it was released with; never `main`), and `ModelManager.modelURL` must match it. The app ships a fine-tune (`tianhaoz95/wee-hours-baby-activity`, tags = training run names), not stock Laya.

**LLM eval and fine-tuning.** `weehours-ci.yml` gates on the keyword model; `weehours-llm-eval.yml` scores the real Laya (llama-server on CPU, `logeval` raw and calibrated, `eval/report.py` vs `eval/results`) only when the questions or the model change (Decision/Interpreter/LayaPrompt/Registry, `spec/event-types.json`, `spec/calibration.json`, `eval/laya.env`, the llama.cpp pin), monthly on the 15th, or by hand, since it's slow. `ml/` fine-tunes Laya on synthetic data (teacher-written utterances for labels fixed in advance, blind-checked, TTS → Whisper base.en with the app's prompt, `laya.train`, GGUF Q8_0). Its labels, Whisper prompt, llama.cpp commit and model URL must match the app (`python -m weehours_ml verify`; tests in `weehours-ml.yml`), so change them together. Before working on the model, read `ml/README.md`: the models shipped so far, label and wording conventions, how to iterate and ship, pitfalls and known weaknesses. Every run's training data is on Hugging Face (`tianhaoz95/wee-hours-baby-activity-data`, `fetch` downloads it), and the eval set is generated by `eval/generate_dataset.py` (edit that, not `spec/utterances.jsonl`). A wording change in `spec/event-types.json` is a prompt change: score it with the shipped model and ship it with a model trained on it. Grouped (care, health, activity) categories reach the model through the category question's "care" option and the `care_type` question (laya's 192-token cap per question); on main they are still `"model": false` until the care round's model ships (branch `weehours-laya-care`).

**Data and sync.** Events are append-only, with corrections written as new events. The phone keeps SQLite in the App Group container (`apps/ios/Shared/SharedStore.swift`), which it shares with the widgets. Sync with Supabase (`Sync.swift`) uses an outbox plus a seq cursor; RLS makes the tables append-only for clients. The tables live in the `weehours` Postgres schema of the shared project (declarative source: repo root `supabase/schemas/weehours/`), so every PostgREST call sends `Accept-Profile`/`Content-Profile: weehours` (supabase-js: `db: { schema }`), and capture audio is in the `weehours` bucket. Accounts (`auth.users`) are shared with the other HEJI apps: create Wee Hours rows on first use, never from triggers on `auth.users`. Local-only mode keeps the household on the phone, and signing in later re-homes the rows. The glasses never run inference: gestures write events directly, and hold-to-speak uploads a *capture* that a household phone processes later. The event id is derived from the capture id, so two phones converge on the same result.

**iPhone app** (`apps/ios/App`, SwiftUI, iOS 18+; iOS 26 features such as Liquid Glass behind `#available`). `AppModel` drives `phase` (signedOut, needsHousehold, ready): `start()` is the once-per-launch setup and `route()` picks the screen from the session and household, so every sign-in path must end with `route()`, never `start()` (calling `start()` again silently left sign-ins on the sign-in screen). The session is in the Keychain, which survives deleting the app: the first launch after an install forgets a leftover session, and household setup always offers "Use a different account". Sign-in: Apple (native sheet, bundle id in the shared project's Apple client ids), Google (Supabase PKCE in the browser sheet, back to `weehours://login-callback`), email only in Debug builds (off project-wide). Release builds use `BackendConfig.production`, Debug the local stack. Launch arguments reach screens without taps (screenshots, checks): `-autoSignIn <email>`, `-localSetup <baby>` (local-only household; `"Mia,Leo"` for twins), `-categories all|bath,potty` (with `-localSetup`: the tracked categories), `-attachAccount <email>`, `-demoText "<transcript>"`, `-screen home|timeline|settings|growth|review|paywall|agents|listening`.

**Care, health and activity types.** Bath, lotion, tooth brushing, potty, teething, medication, symptoms, temperature, doctor visits, vaccinations, tummy time, play and walks are categories marked `"model": false` with a `group` (care, health, activity) and types that describe their own `fields` (choice, number with unit and presets, text) in `spec/event-types.json`. Validation (LogService, `core.ts`), timeline labels, MCP's field docs and the Now tiles (`CareView.swift`: one tap, a menu, or a sheet) all read those fields, so another such type needs only a spec entry. `"model": false` keeps a category out of the decision model's questions (its option texts are the prompt): voice for them waits for training data. Settings → Tracking (grouped) turns each on for the household, which also puts its tile on Now.

**Several children.** A household has any number of children (`weehours.babies`, `Household.babies`; archived ones keep their log). Every event already carries `baby_id`. Derivation runs per child (`DerivedLog(events:baby:)`, `derive(events, baby)`): sessions, next side, status and duplicates are each child's, while undo, edits, resolutions and duty stay household-wide. Each phone chooses which children it shows (`SharedStore.hiddenChildren`) and who Now's buttons log for (the Log-for bar, `AppModel.target`; folds to one line). Logging for several children at once writes one event per child sharing a `group` field, undone together. Voice picks children by name deterministically (`Parsers.children`), else the device's current child. Single-child builds keep working through `my_household()`'s `baby_id`/`baby_name` (the first active child).

**Website and Worker.** `services/web/` is a Vite multi-page site served by a Cloudflare Worker (`wrangler.jsonc`, `src/worker/`). Pages share `src/partials` through a small Vite plugin. `/account` uses supabase-js with the same RPCs and RLS as the app and derives the status line with `@weehours/core`. Pricing and feature claims on the landing page mirror `Subscriptions.storekit` and `Entitlement.allows`, so update both together.

**Agents.** The app records facts and the user's own agent interprets them: there is no in-app advice. The Worker serves the log over MCP at `/mcp` (`src/worker/mcp.ts`) and is its own OAuth 2.1 server (`@cloudflare/workers-oauth-provider`, like Waypack): `/authorize` hands the browser to `/oauth/consent/`, which signs in with Supabase and approves with the session; grants live in the `OAUTH_KV` namespace and the account page lists them via `/api/grants`. Supabase's built-in OAuth server isn't used: it has one consent URL per Supabase project, which every HEJI app shares. Agents that can't do OAuth use `wh_…` personal access tokens (only hashes are stored). Migrating from another tracker: an agent reads the export and calls `import_events` (≤500 entries a call, `dry_run` first, local times read in `timezone`, a `source_id` per row so re-runs skip what's there, per-row errors), `set_tracking` to turn on categories it needs, and `undo_import` to take a whole import back. Imported entries keep `input: "agent"` (installed apps reject unknown input kinds) and carry `import_id` and `import_source` in their provenance. The tool description holds the mapping recipe (sessions become start + finish entries); `scripts/test-mcp.mjs` covers it.

## Verifying and feedback

Check user-facing changes in the app, not only in tests: simulator builds with the launch arguments above and `xcrun simctl io <udid> screenshot`, or a Release build against production on the connected iPhone (`xcrun devicectl device install app`, `device process launch`, `device capture screenshot`; it's registered in the developer team). FeedbackKit reports (project `71d85688-ffc5-481c-8636-2b94dc5c1c90`): put a `FeedbackKit: <id>` trailer on the fix commit, and because FeedbackKit's GitHub App isn't connected to this repo, also run `npx feedbackkit-cli link <id> --commit <sha> --summary "…"`; the next TestFlight upload then ships them (CI announces builds with `WEEHOURS_FEEDBACKKIT_RELEASE_TOKEN`).

## Releasing

**What's New.** Every user-facing feature, fix or improvement goes into `apps/ios/App/Sources/WhatsNewView.swift` in the same change: features in the top release's `features` (shown up front), fixes and polish in `improvementsAndFixes` with `kind: .fix` or `.improvement`. A release prepends a `ReleaseHistoryItem` and sets `currentVersion` to it; never delete older entries (users browse them from Settings → About). The sheet opens once after an update (`shouldShowAutomatically`), not on a fresh install (sign-in and setup mark the version seen). `release.env`'s `release_check` refuses to cut a version What's New doesn't describe.

Cut releases from the repo root with `scripts/cut_release.sh weehours` (settings: `release.env`): it bumps `MARKETING_VERSION` in `apps/ios/project.yml`, pushes (Cloudflare deploys the site + Worker), and publishes GitHub Release `weehours-v<version>`, which runs `.github/workflows/weehours-testflight.yml`. That workflow also runs weekly on Wednesday from `main` and on manual dispatch. It runs `scripts/release_testflight.sh` (also usable locally: `APPLE_TEAM_ID=68CTFST8W2 scripts/release_testflight.sh`) with the team-wide HEJI Apple Development and Apple Distribution identities Waypack uses (`SIGNING_P12_*`, `DEV_SIGNING_P12_*` via `.github/actions/apple-signing`). Never let signing mint new certificates. Build numbers are UTC timestamps. The app is iPhone-only and portrait. App Groups (`group.com.hejitech.weehours`) and Sign In with Apple are registered in the developer portal, and an API key can't create App Groups.
