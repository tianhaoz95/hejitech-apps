    Web App Implementation Walkthrough

    What got built for web/ — scope, how it's wired to the same Firebase project as the Android app, what was actually clicked through and verified (screenshots included), and what's still a TODO.

    Status: Draft, unreviewed Version: v0 Date: July 16, 2026 Owner: Jackson Zhou Depends on: MVP Scope v0, MVP Implementation Walkthrough v0

    1. Scope: Why Web Grew Beyond "Export and Settings"

    MVP Scope v0 originally described the web app as a minimal back-office: export and account settings only, never a capture surface. Two decisions changed the shape of that scope before any code was written:

    • Subscriptions are sold on web only, never via in-app purchase. Skipping IAP entirely on Android/iOS avoids Apple/Google's platform fee on subscription revenue. Neither mobile app will ever contain a purchase flow or pricing mention — they only read entitlement status.
    • Web also becomes the analysis-dashboard surface, using the bigger screen for the kind of charting (trends, per-property/category breakdowns) that doesn't fit the phone's simple pacing view.

    Net effect: web is now three things — subscription/billing, an analysis dashboard, and CPA back-office/export — still never a capture surface. This report, the MVP Scope report (Section 4.4), CLAUDE.md, and web/README.md were all updated to reflect this before any scaffolding started.

    2. What's Built

    A Vite + React + TypeScript single-page app, talking to the same real Firebase project (contempo-platform) and the same Firestore data as android/ — same users/{uid}/entries and users/{uid}/properties collections, same security rules, no backend changes needed.

    PathWhat it is
    web/src/lib/firebase.tsApp/Auth/Firestore init, same emulator-vs-real dual path as Android (VITE_USE_FIREBASE_EMULATOR, defaults on in vite dev)
    web/src/lib/entryModel.tsTypeScript types mirroring the Kotlin Entry/Property models field-for-field (Section 3 has the detail)
    web/src/hooks/useEntries.ts, useProperties.tsRealtime onSnapshot subscriptions, same collection paths and ordering as FirestoreEntryRepository on Android
    web/src/auth/AuthContext.tsxGoogle Sign-In (popup) + auth-state listener + sign-out, exposed via a useAuth() hook
    web/src/billing/subscription.tsStripe integration stub — see Section 6
    web/src/components/charts/BarChart, ThresholdProgress, TrendSparkline — hand-rolled SVG/HTML, no charting library (Section 4)
    web/src/pages/DashboardPage, EntriesPage, BillingPage, SettingsPage, SignInPage
    web/src/styles/tokens.css, charts.cssDesign tokens, ported from the landing page (Section 4)
    scripts/run-web-with-emulators.shLocal dev loop — emulators + Vite dev server, torn down together (Section 5)

    3. Data Model: Read From the Real Android Schema, Not Guessed

    Before writing any TypeScript types, the exact Firestore document shape was pulled from android/core/src/main/java/com/hejitech/core/model/Entry.kt and Property.kt — not from backend/functions/src/schemas.ts, which is a narrower AI-parsing shape, not what's actually stored once the app layers on bookkeeping fields.

    PathFields
    users/{uid}/entries/{id}propertyId, propertyName, task, durationMinutes, category, status, source, activityDate, loggedAt, confirmedAt, isVague, isBackfilled, daysLate, riskReasons[], photoUrls[]
    users/{uid}/properties/{id}name, createdAt
    The app hardcodes one test, not three Planning docs mention the 100hr/500hr STR tests and the 750hr REPS test, but MaterialParticipationTest.kt only implements the 100-hour STR test — there's no REPS/500hr variant in the app yet, and no "projected finish date at current pace" calculation either (also planning-doc aspiration, not built). The web dashboard deliberately doesn't invent a test-picker or a pacing projection the app itself can't back up — entryModel.ts's MATERIAL_PARTICIPATION_TEST constant is hardcoded to match, with a comment explaining why.

    4. Design System: Brand Chrome + a Validated Data Palette

    web/src/styles/tokens.css ports the landing page's pine/navy/brass palette exactly — same CSS custom properties, same three-declaration-site theme pattern (@media (prefers-color-scheme: dark) plus explicit [data-theme] overrides so the toggle wins either way). A small ThemeToggle component persists the choice to localStorage.

    Charts are a different problem: the brand only has three hues (pine, navy, brass) — not enough distinct, CVD-safe slots for the six entry categories a bar chart needs to show side by side. Rather than eyeball a six-color set out of three hues, the dashboard uses the data-viz skill's validated default 8-hue categorical theme (first six slots, fixed order, never cycled) for chart data, while chart chrome (surface, gridlines, ink) stays on the brand's own tokens. This was re-validated against this app's actual surface color, not assumed from the skill's own defaults:

    ModeResult
    Light, surface #ffffffAll checks pass. CVD separation and normal-vision floor both clear; contrast is a WARN on 3 of 6 slots (magenta/yellow/aqua sit under 3:1) — mitigated by shipping direct value labels on every bar, never relying on color alone
    Dark, surface #16201cAll checks pass clean, including contrast

    Single-value encodings (threshold progress, the flagged-entries trend line) use the brand's pine accent directly rather than the categorical set — a single series needs no palette, just one hue and a title.

    5. Local Dev: run-web-with-emulators.sh, and a Real Bug It Surfaced

    Mirrors run-android-with-emulators.sh's shape — start the Firebase emulator suite, wait for ready, start the app, tear both down together on Ctrl+C — but simpler, since a browser talking to localhost needs no adb reverse-style port forwarding the way a physical Android device does.

    The default project argument was wrong, and it silently broke everything The script originally defaulted to demo-contempo (matching the Android script's placeholder) independent of whatever project web/.env.local was configured for (contempo-platform, the real registered app). The Firestore and Auth emulators partition data by project id — a client configured for one project id gets a completely separate, empty namespace from another, even against the same running emulator process. Seeding sample data via the Admin SDK under demo-contempo and then loading the dashboard (configured for contempo-platform) produced a dashboard that rendered correctly but showed 0.0h everywhere — not an error, just silently empty. Confirmed directly by querying both project namespaces with the Admin SDK: 20 seeded entries existed under demo-contempo, 0 under contempo-platform. Fixed by having the script read VITE_FIREBASE_PROJECT_ID out of web/.env.local and use that as the default (falling back to demo-contempo only if that file doesn't exist), and by correcting the script's own mismatch warning, which had previously (and wrongly) claimed a mismatch was harmless.

    6. Stripe: Deliberately Not Done

    web/src/billing/subscription.ts is a stub: getSubscriptionStatus() always returns "none", with a TODO(stripe) comment describing the plan (Stripe's official "Run Payments with Stripe" Firebase Extension, syncing subscription status into a Firestore doc every client reads). BillingPage reads this stub and renders three illustrative pricing tiers (kept identical to the landing page mockup's Starter/Pro/Portfolio tiers) with disabled "Coming soon" buttons — no checkout flow exists yet, by design, until Stripe is actually configured.

    7. What Was Actually Verified (Not Just Written)

    Same standard as the Android implementation report: this section describes what was actually run, with evidence, not what was expected to work.

    1. npm run build (tsc -b && vite build) passes clean. Bundle is 799 KB / 242 KB gzipped — Vite warns about chunk size (mostly the Firebase SDK); not code-split yet, flagged as a real gap in Section 8, not fixed.
    2. Full sign-in-to-dashboard flow, automated with Playwright against a headless Chromium, not just started and eyeballed: launched scripts/run-web-with-emulators.sh, drove the actual "Sign in with Google" button, which — with the Firebase Auth emulator connected — opens the emulator's own fake Google IDP widget rather than real Google; created a test account there, landed back on /dashboard correctly authenticated.
    3. Seeded realistic sample data via the Admin SDK (2 properties, 20 entries spanning ~10 weeks, mixed status/category/flags) directly into the signed-in test user's uid, matching the exact schema from Section 3 — this is what caught the project-id bug in Section 5.
    4. Screenshotted every page in both themes with real data: Dashboard (threshold progress showing 30.6/100h, a real flagged-entries trend line, populated property/category bar charts with correct validated colors and direct labels), Entries (filtered list, risk flags in the brand's danger red), Billing (three tiers, disabled buttons). Light and dark both confirmed to swap every token correctly, including the chart categorical colors.
    5. Exercised the "view as table" toggle on both bar charts — confirmed it swaps to a real data table, not a placeholder.
    6. Exercised CSV export end-to-end — clicked "Export CSV", captured the actual browser download event, and read back the file's real content (header row plus correctly formatted property/date/task/category/ duration/status/flagged columns) rather than just confirming a click handler exists.
    7. No console errors or uncaught exceptions were logged by the app during any of the above (checked via Playwright's console/pageerror listeners across every run, not just visually).

    8. What's NOT Done or NOT Verified

    • Stripe/billing is entirely unimplemented — see Section 6. No checkout, no webhook, no real entitlement sync.
    • Real (non-emulator) Google Sign-In against the actual contempo-platform project was never clicked through — only the Auth emulator's fake IDP widget was exercised. The real popup flow (real Google OAuth consent screen) should work since the same app registration and auth.providers.googleSignIn config back both Android and web, but hasn't been directly tested against production.
    • No property-management UI — properties are read-only in the dashboard/filters; creating/editing a property still requires the Android app.
    • Corrections collection has no reader — matches the Android side (write-only, training signal for later), not a web gap specifically.
    • No code-splitting — single 799 KB JS bundle; fine at current scale (single pilot user), worth revisiting before this needs to serve real traffic.
    • No automated test suite committed — verification in Section 7 was a one-off Playwright script run from a scratch directory, not checked into the repo as a repeatable test.
    • Print/PDF view was implemented (window.print() plus print-only CSS) but not visually verified — headless Chromium doesn't render a print preview the same way a real browser's print dialog does, so this is unverified beyond "the code path exists and doesn't throw."

    9. How to Run It

    1. cd web && npm install (one-time)
    2. Copy web/.env.example to web/.env.local and fill in the Firebase web app config — fetch it with npx -y firebase-tools@latest apps:sdkconfig WEB <APP_ID> --project contempo-platform.
    3. ./scripts/run-web-with-emulators.sh — starts the Firebase emulator suite (defaulting to whatever project .env.local is configured for) and the Vite dev server together, tears both down on Ctrl+C. Pass a project id explicitly to override.
    4. Open the printed http://localhost:5173/ URL, click "Sign in with Google" — against the emulator this opens a fake IDP widget where any email works; against a real project it's the real Google consent screen.

    10. Immediate Next Steps

    • Configure Stripe and replace the subscription.ts stub — the natural next milestone, since everything else in Billing already assumes its shape
    • Click through real (non-emulator) Google Sign-In against the live contempo-platform project at least once
    • Decide whether property management belongs on web or stays Android-only as usage grows past the current single-pilot-user scale
    • Commit a real test (even a minimal Playwright smoke test) so the sign-in → dashboard → export path stays checked automatically instead of re-verified by hand each time
    • Revisit bundle size/code-splitting once this needs to serve more than a pilot user
